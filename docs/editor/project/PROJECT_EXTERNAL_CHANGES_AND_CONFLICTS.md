# Project External Changes and Conflicts

NovelTea projects are ordinary source trees, so the editor must coexist with file edits made by coding agents, source-control tools, and other editors. The project workspace watcher and reconciliation layer are the authority for those changes; there is no separate asset-only watcher and no whole-project content-fingerprint conflict gate.

## Watching and coherent publication

The main process owns one project-root watcher in `editor/src/main/services/project-workspace-watcher-service.ts`. Every observed path is classified exactly once as authoring source, asset source, transaction observation, or ignored state. `.noveltea/` generated/local state and project-local `workflows/` are ignored except for transaction-settling observation. Canonical authored source is limited to the workspace manifests/fragments, `records/**`, and `scripts/**`; unrelated root files such as notes or agent documentation do not enter reconciliation. Asset routing includes both the conventional `assets/**` tree and every explicit project-relative Asset source path discovered from the loaded project, so a tracked source such as `images/custom/source.webp` is still treated as an asset rather than authoring JSON. After a successful authoring-source reassembly, the watcher replaces that routing set directly from the authoritative assembled `AuthoringProject`, so changing an Asset record from one custom source path to another immediately retires the old path and observes the new one without reparsing a stripped persistence projection. Asset-source events never directly invoke authoring-document reconciliation. A mixed settled batch reconciles authoring source first and then audits assets against the reconciled document. The fixed chokidar settling contract is a 200 ms await-write stability threshold with a 50 ms poll interval followed by a 150 ms quiet batch before publication. The short stability window still waits for file size to stop changing, so large direct writes settle after completion while ordinary JSON/Lua/RML edits normally become visible well below one second after the final write.

A settled batch is assembled through `ProjectWorkspaceService` before the renderer sees it. Asset-only batches may refresh canonical workspace/file revision metadata, but they do not replace the working or saved authoring document. If a tracked asset source is deleted or otherwise makes the assembled candidate invalid, the last coherent authoring project remains loaded and the failure is surfaced as an Asset source diagnostic instead of being ignored or published as an empty project. Structurally invalid JSON, a missing authoritative source, an unsupported workspace version, or an unresolved transaction-recovery conflict never replaces the last coherent editor project. While an authoritative tracked source is structurally unreadable, tracked project writes fail closed because the editor cannot assemble the current disk workspace needed for scoped ownership and revision checks. When a later watcher batch proves the workspace valid again, the latched external-source diagnostic is cleared even when the repaired bytes return to the editor's already-known workspace revision. A committed NovelTea transaction is published as one logical change rather than as a sequence of intermediate file events.

## Revisions and three-way reconciliation

Authoritative workspace files use exact-byte `sha256:<hex>` revisions, with `absent` representing an expected missing path. `workspaceRevision` is the deterministic aggregate of the canonical source-file revision inventory. Ignored editor-local/session state is excluded from both loaded and in-memory workspace identity; tracked `editor.json` organization remains part of that identity. Scoped saves use the exact physical file revisions owned by their selected logical save units plus the exact JSON paths changed by the selected recovery component; the aggregate revision is not a whole-project overwrite token.

For every affected logical save unit reconciliation compares:

- `B`: the editor's last common saved baseline;
- `L`: the current local working value;
- `E`: the newly assembled external disk value.

If the editor is clean, `E` becomes both baseline and working state. If local and external deltas from `B` touch disjoint logical paths, the local delta is rebased onto `E`, the saved baseline advances to `E`, and the unit remains dirty only for the rebased local work. This same path-level rule is applied inside an explicit Save transaction: the main process verifies only the selected changed paths against `B`, overlays those paths onto the newest disk snapshot, and can therefore preserve an external change to another field in the same Room JSON file. Equal or ancestor/descendant JSON paths conflict. Insert/remove/reorder changes under the same array root are conservatively conflicting.

Independent records and independent logical owners inside the same physical file, such as chapter, tag, and record-metadata state in `editor.json`, reconcile independently. After any successful manual or structural content write, the main process returns the authoritative post-commit assembled project. The renderer performs the same B/L/E reconciliation against that returned snapshot before adopting its revisions; this closes the race where a concurrent external edit could otherwise be hidden because the renderer learned the newest revision before learning the newest content. External create/delete updates clean records normally; deleting a locally dirty record conflicts.

## Conflict state and resolution

Overlapping changes preserve `B`, `L`, and `E` in ignored editor recovery state and block ordinary Save for that save unit. The conflict dialog identifies the affected unit and logical paths and offers:

- **Use Disk**: discard only that unit's local conflicting delta, adopt `E` as working state and baseline, and preserve unrelated dirty units.
- **Keep Mine**: explicitly commit the selected local result against the current external file revisions. If disk changes again before the commit, nothing is overwritten; the editor re-reads and keeps the unit conflicted against the new external state.
- **Cancel**: retain the conflict and local work unchanged.

Conflict recovery is save-unit state, not a global dirty flag. `.noveltea/editor/state.json` records the tracked `workspaceRevision` against which its recovery overlay was produced. Closing/reopening normally restores valid recovery entries against that same baseline. If tracked source changed while the editor was closed and the saved baseline revision is therefore stale, recovered local values remain visible but each affected recovery unit is reopened as an explicit conflict requiring **Use Disk** or **Keep Mine**; NovelTea does not guess a three-way base and does not silently overwrite the newer disk state. Corrupt or unsupported local state is discarded rather than used to mutate tracked source.

## Transaction recovery and writer locking

NovelTea-owned tracked writes serialize through `.noveltea/transactions/.writer-lock/` and journal multi-file changes under `.noveltea/transactions/<id>/`. Asset import/reimport/trash/restore operations use the same revision-CAS transaction layer: a move's source precondition is the hash of the exact bytes captured for the move, destinations that must be empty use the explicit `absent` precondition, and intentional replacement such as reimport carries the destination revision captured before the replacement interaction. Helpers never discover a newer source/destination revision after operation intent has already been established. A clean workspace open with no transaction entries performs no recovery mutation and does not manufacture a writer lock. If recovery work exists, a live or unverifiable lock owner fails closed with `WORKSPACE_BUSY`; a proven-dead owner is reclaimed only after transaction recovery. Missing/malformed journals, or a target whose bytes match neither the recorded before nor after revision, are retained and block mutation with `WORKSPACE_TRANSACTION_RECOVERY_CONFLICT`; recovery never overwrites an unknown external edit.

Raw external editors do not honor the NovelTea writer lock, so every NovelTea write still verifies expected target revisions immediately before replacement.

The regression matrix lives primarily in `project-workspace-watcher-service.test.ts`, `workspace-new-project.test.tsx`, external reconciliation/conflict tests under `editor/src/renderer/test/`, save/recovery tests, and `project-workspace-transactions.test.ts`.
