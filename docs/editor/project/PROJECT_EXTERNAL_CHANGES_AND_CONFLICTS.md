# Project External Changes and Conflicts

NovelTea projects are ordinary source trees, so the editor must coexist with file edits made by coding agents, source-control tools, and other editors. The project workspace watcher and reconciliation layer are the authority for those changes; there is no separate asset-only watcher and no whole-project content-fingerprint conflict gate.

## Watching and coherent publication

The main process owns one active-session-bound project-root watcher in `editor/src/main/services/project-workspace-watcher-service.ts` and one `ActiveProjectWorkspaceSession` for the active `projectSessionId`. Initial project open performs the cold authoritative authoring-source assembly and seeds that live session. Thereafter the session retains the coherent parsed project, per-authoring-file exact revisions, source ownership/index data, and cached source reads. Renderer code starts and stops the watcher with the opaque session id; main derives the root from active authority, and watcher events carry that session id rather than a renderer-comparable root or manifest path. Every observed path is classified exactly once as authoring source, asset source, transaction observation, or ignored state. `.noveltea/` generated/local state and project-local `workflows/` are ignored except for transaction-settling observation. Canonical authored source is limited to the workspace manifests/fragments, `records/**`, and `scripts/**`; unrelated root files such as notes or agent documentation do not enter reconciliation. Asset routing includes both the conventional `assets/**` tree and every explicit project-relative Asset source path discovered from the loaded project, so a tracked source such as `images/custom/source.webp` is still treated as an asset rather than authoring JSON. Binary Asset source bytes are deliberately outside the authoring workspace revision inventory and are not synchronously hashed during project open or ordinary authoring saves. An Asset source is hashed when an Asset operation requires exact identity or when the watcher reports that specific Asset path changed. After a successful authoring-source reassembly, the watcher replaces the Asset routing set directly from the authoritative assembled `AuthoringProject`. Asset-source events never directly invoke authoring-document reconciliation. A mixed settled batch reconciles authoring source first and then audits assets against the reconciled document. The fixed chokidar settling contract is a 200 ms await-write stability threshold with a 50 ms poll interval followed by a 150 ms quiet batch before publication. The short stability window still waits for file size to stop changing, so large direct writes settle after completion while ordinary JSON/Lua/RML edits normally become visible well below one second after the final write.

A settled authoring batch invalidates only the physical paths reported by chokidar and reassembles through the live session's caching filesystem. Unchanged authoring text and exact revisions are reused; changed files are reread/rehashed once after they settle. The main process computes the logical authoring delta between the previous and new coherent project and sends only those affected paths/values and involved physical revisions to the renderer. Whole-project watcher candidates are reserved for initial load/full resynchronization, not normal external edits. A successful batch must still belong to the same active Project authority before publication. Failed or structurally unreadable source reports diagnostics without replacing the last coherent admitted project. The session separately records that the current physical source is invalid. Saves that directly own that physical file, or whose existing authoring dependency reverse-closure depends on the invalid logical owner, fail closed; unrelated save units remain writable. An invalid `project.json` or an unattributable structural/inventory failure blocks all tracked writes. If a referenced Asset source disappears, the last coherent authoring project remains loaded and the watcher publishes an Asset-source diagnostic rather than treating the binary as authoring state. When source becomes valid again, the latched diagnostic is cleared. If watcher trust is lost through a watcher error or system resume, the session performs a cheap authoring-file metadata/inventory resynchronization and rehashes only suspicious/new files; it does not answer watcher uncertainty with a binary-asset or whole-workspace hash sweep.

## Revisions and three-way reconciliation

Authoritative authoring files use exact-byte `sha256:<hex>` revisions, with `absent` representing an expected missing path. Stateless workspace tooling may still derive an aggregate `workspaceRevision`, but active-editor synchronization does not expose or compare that aggregate and does not replace it with another global generation counter. Exact hashes answer the narrow question “are these exact physical bytes still the bytes this operation was based on?” Renderer `projectRevision` remains the in-memory authoring-document revision used by authoring services such as the dependency graph; persistence-only Save does not advance it. Ignored editor-local/session state is outside tracked authoring identity; tracked `editor.json` organization remains an ordinary authoring source.

For every affected logical save unit reconciliation compares:

- `B`: the editor's last common saved baseline;
- `L`: the current local working value;
- `E`: the newly assembled external disk value.

If the editor is clean, `E` becomes both baseline and working state. If local and external deltas from `B` touch disjoint logical paths, the local delta is rebased onto `E`, the saved baseline advances to `E`, and the unit remains dirty only for the rebased local work. This same path-level rule is applied inside an explicit Save transaction: the main process verifies only the selected changed paths against `B`, overlays those paths onto the newest disk snapshot, and can therefore preserve an external change to another field in the same Room JSON file. Equal or ancestor/descendant JSON paths conflict. Insert/remove/reorder changes under the same array root are conservatively conflicting.

Independent records and independent logical owners inside the same physical file, such as chapter, tag, and record-metadata state in `editor.json`, reconcile independently. Save IPC contains only the selected save units, affected logical paths, and their `B`/`L` values. Main overlays those values onto the live disk-side session project and validates the result in memory. A successful ordinary Save returns a targeted persistence acknowledgement: committed units, revisions for involved physical files, diagnostics, and only any external logical values that were discovered while resolving a transaction race. It does not return/reload the whole project. If exact target CAS loses a race, main refreshes only that target, performs the same path-level comparison, retries once for a disjoint edit, and returns the discovered external delta so renderer reconciliation cannot miss it. External create/delete updates clean records normally; deleting a locally dirty record conflicts.

Foreground editor-owned saves do not wait for the workspace watcher's write-stability or quiet-period timers and do not call `ProjectWorkspaceService.open()` on the common active-session path. The session already owns the coherent disk baseline. Main applies the selected logical mutation in memory, derives the union of before/after physical targets, and the transaction layer freshly hashes only those target files for exact CAS immediately before replacement (and again before application as required by the transaction protocol). Post-commit source revisions for bytes NovelTea just wrote are derived from those already-known bytes and synchronously adopted into the session. The final recovery/local editor state is then written once. Chokidar's later event for a NovelTea-owned source compares the observed exact revision with the session's known post-write revision; a match is a no-op, while different bytes are a genuine subsequent external edit. Never reintroduce a full workspace open, directory walk, unrelated authoring-file hash, or Asset hash into ordinary Ctrl+S.

## Conflict state and resolution

Overlapping changes preserve `B`, `L`, and `E` in ignored editor recovery state and block ordinary Save for that save unit. The conflict dialog identifies the affected unit and logical paths and offers:

- **Use Disk**: discard only that unit's local conflicting delta, adopt `E` as working state and baseline, and preserve unrelated dirty units.
- **Keep Mine**: explicitly commit the selected local result against the current external file revisions. If disk changes again before the commit, nothing is overwritten; the editor re-reads and keeps the unit conflicted against the new external state.
- **Cancel**: retain the conflict and local work unchanged.

Conflict recovery is save-unit state, not a global dirty flag. Each dirty recovery save unit in `.noveltea/editor/state.json` records only the exact physical baseline revisions it depends on. There is no root `workspaceRevision` in the local-state format. On reopen, NovelTea checks those recovery-dependent files only. If one changed while the editor was closed, recovered local values remain visible but that affected recovery unit reopens as an explicit conflict requiring **Use Disk** or **Keep Mine**; unrelated source changes do not invalidate it. When one successful save changes a physical file shared by another dirty logical owner (for example `editor.json`), the remaining unit's persisted baseline revision advances to the newly committed physical revision. NovelTea does not persist historical three-way base snapshots or guess a base after restart. The local-state format is an internal hard cutover; unsupported local state is discarded rather than migrated into tracked source.

## Transaction recovery and writer locking

NovelTea-owned tracked writes serialize through `.noveltea/transactions/.writer-lock/` and journal multi-file changes under `.noveltea/transactions/<id>/`. Asset import/reimport/trash/restore operations use the same revision-CAS transaction layer: a move's source precondition is the hash of the exact bytes captured for the move, destinations that must be empty use the explicit `absent` precondition, and intentional replacement such as reimport carries the destination revision captured before the replacement interaction. Helpers never discover a newer source/destination revision after operation intent has already been established. Transaction-path watcher noise alone does not cause a workspace reassembly: once the writer lock is gone, the live session checks whether a real journal remains. With no pending journal it does nothing. If an orphan journal exists, recovery is serialized through the same session mutation lane, after which only authoring files whose exact revisions actually changed are published. A clean workspace with no transaction entries performs no recovery mutation and does not manufacture a writer lock. If recovery work exists, a live or unverifiable lock owner fails closed with `WORKSPACE_BUSY`. A proven-dead lock is reclaimed only by the process that first acquires the exclusive reclaim guard and atomically claims the stale lock directory; owner identity/liveness is revalidated under that guard, competing reclaimers cannot enter journal recovery, and every claimed/active directory removal verifies its owner token. Missing/malformed journals, or a target whose bytes match neither the recorded before nor after revision, are retained and block mutation with `WORKSPACE_TRANSACTION_RECOVERY_CONFLICT`; recovery never overwrites an unknown external edit.

Raw external editors do not honor the NovelTea writer lock, so every NovelTea write still verifies expected target revisions immediately before replacement.

## Verification

The regression matrix lives primarily in `project-file-service.test.ts`, `project-workspace-watcher-service.test.ts`, `workspace-new-project.test.tsx`, external reconciliation/conflict tests, save/recovery tests, and `project-workspace-transactions.test.ts`. In addition to reconciliation behavior it enforces architectural performance invariants: an active scoped Save performs zero workspace opens, exact revision reads are limited to its transaction targets, cold authoring load does not hash referenced binary Assets, a persistence-only Save does not advance renderer `projectRevision` or publish a dependency-graph mutation, and NovelTea's own post-write revision is recognized as a watcher no-op. Coverage also includes invalid-source direct/dependency scoping, watcher-trust resynchronization discovering a missed new source, orphan-journal recovery with no-op clean transaction observation, low-latency settling, dynamic Asset routing, asset-only audit, missing tracked assets, invalid-to-valid source recovery, tracked `editor.json` reconciliation, disjoint same-record Save merging, same-path conflict, conservative arrays, per-unit recovery baselines, create/delete, Asset move/replacement revision preconditions, transaction coalescing, Use Disk, Keep Mine, a second edit during Keep Mine, immediate Save versus recovery debounce, and ignored `.noveltea/`/`workflows/` changes.
